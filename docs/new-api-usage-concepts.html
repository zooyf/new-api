new-api usage graph

用量链路里的 User、Group、Channel、Model、Type 与 API Key

这几个概念不是平级字段，而是一次 API 调用从“谁在调用”到“走哪个 endpoint、哪个 helper、哪个上游渠道”再到“如何计费、如何落用量明细”的完整坐标系。

核心概念 关系总览 Channel Type Endpoint 形态 详细判定流程图 Path2RelayMode Group 规则 生产例子

核心概念

字段名按 new-api 代码和数据库模型口径描述；其中 API Key 在代码里主要叫 Token。

UUser 用户

平台账号实体，代表谁拥有额度、谁创建 API Key、谁在后台看到消费。用户只有一个默认分组。

users.id username group quota used_quota

KAPI Key / Token

客户请求时携带的凭证。它属于某个 User，可以指定本 key 使用的目标 group，也可以限制模型、IP、过期时间和额度。

tokens.id user_id key name group model_limits

GGroup 分组

单次请求最终只会落到一个 effective group。这个 group 同时参与渠道候选、客户倍率、模型权限和日志归属。

users.group tokens.group channels.group group_ratio

CChannel 渠道

上游供应商配置。渠道通过 group 声明服务范围，通过 models 声明能承接哪些模型，通过 type 声明用哪个适配器。

channels.id name type base_url models

MModel 模型

下游请求里的模型名。它先参与 key 模型限制和渠道候选，再可能通过模型映射转换成上游模型名。

request.model model_mapping origin_model upstream_model

Tchannels.type

它不是 usage log 里的 type，而是渠道的协议/供应商适配器类型。选中 channel 之后，type 决定用哪个 adaptor 发上游。

type=54 DoubaoVideo type=58 AdvancedCustom 普通 adaptor task adaptor

关系总览

恢复了原来的核心关系图，并把线条拉开：User 拥有 Token；Token 解析出 effective group；group + model 选 Channel；Channel 发上游并落用量明细。

Channel Type 与 Endpoint 的关系

客户访问的 endpoint 先决定“这是什么调用形态”，选中渠道后，channels.type 再决定“如何把这个调用发给上游”。

判断顺序：先看客户打到哪个 endpoint，再看请求 body 或 path 里的 model，随后用 group + model 选 channel，最后才由 channels.type 决定“这个 channel 如何访问上游”。所以 type 与 endpoint 是协作关系，不是一对一绑定关系。
客户 endpoint 先得到的调用形态 channels.type 的作用 例子
POST /v1/chat/completions ChatCompletions 文本/多模态同步调用。 决定转成 OpenAI、Claude、Gemini、通义、火山等哪家上游协议。 Claude 渠道会把 OpenAI 兼容请求转成 Anthropic Messages；Gemini 渠道会转成 Gemini 格式。
POST /v1/images/generations 图片生成调用。 决定上游图片接口路径和图片参数转换方式。 OpenAI、阿里、火山等图片接口字段和 URL 可能完全不同。
POST /v1/video/generations 异步视频任务提交。 通过 task adaptor 决定是 DoubaoVideo、Sora、Kling、Vidu 等任务协议。 Seedance 渠道应选 DoubaoVideo 这类支持豆包视频任务语义的 type。
GET /v1/video/generations/{task_id} 异步视频任务查询。 根据 task/platform/channel type 找对应查询 adaptor，并在成功后触发重算或退款。 提交和查询必须能回到同一类 task adaptor，否则状态和 usage 解析可能不对。
自定义 path 取决于路由是否已注册，或是否由独立代理接住。 Advanced Custom 可以配置 incoming/upstream path；素材库透传则走独立服务。 /api/v3/open/CreateAsset 由 Nginx 转发到 hwdrama-proxy，不进主 relay helper。

详细判定流程图

这张图只表达执行顺序：从 HTTP 请求进入，到 Router、中间件、请求语义解析、选渠道，再分流到普通 helper 或 task adaptor。详细解释放在图后面，按 0 到 7 顺序展开。

先把业务流程排直：这条链路不是并行图，也不是 Router 反向指向 HTTP。正确顺序是：HTTP 请求先进入 Gin Router，Router 命中具体 endpoint 后才执行该路由上的中间件；TokenAuth 负责识别用户和 key，Distribute 先从 body/path/query/route param 解析 model、group、relay_mode，再用 group + model 选 channel，最后 controller/helper/task adaptor 只使用已经选好的 channel 去访问上游。

0. HTTP 入口：endpoint 形态

先解释图里的第 0 步。endpoint 形态按代码入口定义，不按供应商名字定义；当前文档把生产关心的入口收敛成 7 类。

0-A. 模型列表/模型查询 GET /v1/models GET /v1/models/{model} GET /v1beta/models 返回模型，不进入普通 relay helper。
0-B. OpenAI 兼容同步调用 /v1/chat/completions /v1/responses / /v1/embeddings /v1/images/* / /v1/audio/* 进入 controller.Relay，主要靠 Path2RelayMode 推断 RelayMode。
0-C. Playground 调用 POST /pg/chat/completions 走用户会话鉴权，不走 API Key；随后仍按 chat relay 处理。
0-D. Gemini 原生路径 /v1beta/models/* /v1/models/* /v1/engines/:model/embeddings 从 path 提取模型，设置 RelayModeGemini。
0-E. 视频异步任务 POST /v1/video/generations GET /v1/video/generations/{id} /v1/videos / /v1/videos/{id} Distributor 设置 RelayModeVideoSubmit/Fetch。
0-F. 供应商兼容任务入口 /mj/* / /suno/* /kling/v1/videos/* /jimeng 中间件把供应商格式转成内部任务语义，或设置 platform / relay_mode。
0-G. 非主 relay 的独立代理 /api/v3/ark/* /api/v3/open/* 例如素材库透传服务，经 Nginx 转到 hwdrama-proxy，不进入主 relay helper。

阶段说明

下面继续按图中编号说明 0 到 7。每一行的关键输入都来自前面阶段的关键输出；第 0 步是链路起点，因此没有上一阶段。

阶段 关键输入 做什么 关键输出 下一步
0. HTTP Request 链路起点：客户发来的 HTTP 请求，没有上一阶段输入。 接收原始请求；全局中间件会先处理 CORS、解压、请求体存储、统计等通用行为。 method、path、query、headers、body、content_type。 交给 Gin Router 用 method + path 匹配具体路由。代码入口见 router/relay-router.go、router/video-router.go。
1. Router 匹配 endpoint 来自第 0 步输出的 method、path。 Router 按注册表决定请求属于哪类入口：普通 OpenAI 兼容 relay、视频任务 relay、Gemini 原生路径、MJ/Suno/Kling/Jimeng 任务路径，或者非主 relay 的独立代理。 命中的 handler，例如 controller.Relay、RelayTask、RelayTaskFetch；命中的 relayFormat；路由参数如 :model、:task_id、:action；以及该路由挂载的中间件链。 执行该路由上的鉴权中间件。普通 API key 路由进入 TokenAuth；Playground 进入 UserAuth 后再进入 Distribute。
2. TokenAuth 来自第 0 步输出的 headers、query、path，以及第 1 步输出的中间件链。 识别 API Key，校验 token 状态、过期、额度、IP、模型限制等，并把用户和 token 上下文写入 Gin context。 AuthContext：user_id、user.group、using_group、token_id、token.group、token quota、模型限制、跨分组重试标记、可选 specific_channel_id。 进入 Distribute。相关代码见 middleware/auth.go 的 TokenAuth 和 SetupContextForToken。
3. Distribute 解析请求语义 来自第 0 步输出的 path、query、body、content_type；来自第 1 步输出的路由参数；来自第 2 步输出的 AuthContext.user_id 和模型限制上下文。 getModelRequest 根据路径和 Content-Type 解析模型。JSON 请求用 gjson 读取 model/group；Gemini 原生路径从 path 提取模型；视频提交从 body 读取模型；视频查询在需要模型限制校验时从已存任务回填原始模型；图片、音频、moderation 会按代码补默认模型或 relay_mode。 RequestSemantic：modelRequest.Model、modelRequest.Group、shouldSelectChannel、relay_mode、platform、任务查询时回填的原始模型。 进入同一个 Distribute 中的渠道选择逻辑。相关代码见 middleware/distributor.go 的 getModelRequest、getModelFromRequest、getModelFromJSONBody。
4. Distribute 选择 channel 来自第 2 步输出的 AuthContext，来自第 3 步输出的 RequestSemantic.model/group/shouldSelectChannel，以及第 0 步输出的 path。 先做 token 模型限制校验；再确定实际使用分组；如果 token 指定了渠道则校验该渠道，否则使用 affinity 或 CacheGetRandomSatisfiedChannel 根据 group + model + requestPath 找可用渠道；最后调用 SetupContextForSelectedChannel 写入渠道上下文。 ChannelContext：original_model、channel_id、channel_name、channels.type、channel.base_url、上游 key、模型映射、参数覆盖、请求头覆盖、状态码映射、request_start_time。 进入第 1 步已经命中的 controller。相关代码见 middleware/distributor.go 的 Distribute 和 SetupContextForSelectedChannel。
5. Controller 分支 来自第 1 步输出的 handler/relayFormat，来自第 3 步输出的 relay_mode/platform，来自第 4 步输出的 ChannelContext。 根据路由 handler 进入普通同步 controller 或异步任务 controller：普通 OpenAI/Claude/Gemini/Image/Audio 路径进入 controller.Relay；视频、Suno、Kling、Jimeng 等任务路径进入 RelayTask 或 RelayTaskFetch。 分叉方向：6A 普通同步 relay，或 6B 异步任务 relay。 普通同步继续构建 RelayInfo 并用 Path2RelayMode 选择 helper；异步任务继续构建 task relay 运行时并选择 task adaptor。
6A. 普通同步 relay 来自第 5 步输出的普通同步分支，来自第 4 步输出的 ChannelContext，来自第 0 步输出的 body/path/headers，以及第 3 步输出的 relay_mode 兜底值。 controller.Relay 校验并解析请求 DTO，GenRelayInfo 从 context 组装 RelayInfo；genBaseRelayInfo 先用 Path2RelayMode(path) 推断 RelayMode，未知时回退到第 3 步设置的 relay_mode；随后计费预扣、重试选渠道，relayHandler 根据 RelayMode 选择 Text/Image/Audio/Responses 等 helper。 SyncRelayRuntime：校验后的请求 DTO、RelayInfo、PriceData/预扣费会话、选中的 helper、由 channels.type 初始化的普通 adaptor。 进入第 7 步，由普通 adaptor 组装上游请求、调用上游、解析响应和 usage。相关代码见 controller/relay.go、relay/common/relay_info.go、relay/constant/relay_mode.go。
6B. 异步任务 relay 来自第 5 步输出的异步任务分支，来自第 4 步输出的 ChannelContext，来自第 0 步输出的 body/path，以及第 3 步输出的 relay_mode/platform/model。 controller.RelayTask 或 RelayTaskFetch 构建 task RelayInfo；提交路径会先 ResolveOriginTask，再进入 RelayTaskSubmit；RelayTaskSubmit 用 platform 或 GetTaskPlatform 找 task adaptor，调用 ValidateRequestAndSetAction，再应用模型映射和任务计费逻辑。 TaskRelayRuntime：选中的 task adaptor、任务 action、OriginModelName/UpstreamModelName、预扣费上下文、公开任务 ID、上游任务请求或查询响应构造器。 进入第 7 步，由 task adaptor 提交上游任务或查询任务状态。相关代码见 controller/relay.go、relay/relay_task.go、relay/channel/task/*。
7. adaptor 发上游，解析响应 / usage 来自第 6A 输出的 SyncRelayRuntime 或第 6B 输出的 TaskRelayRuntime，以及来自第 4 步输出的 ChannelContext。 adaptor 组装上游 URL、headers、body，发送请求，解析响应。同步接口解析 usage 后结算；异步任务提交时预扣并记录任务，完成或失败后按任务终态重算、退款或写任务日志。 客户响应、上游响应、usage、任务状态、quota 消费/退款日志。 返回客户；同时写 usage log、task 或 billing 相关记录。

Path 推断 RelayMode 的实现逻辑

实现位于 relay/constant/relay_mode.go。普通同步接口先由 Path2RelayMode(path) 归类；视频等任务入口主要由 Distributor 或转换中间件设置 relay_mode。

Path2RelayMode 规则 RelayMode 后续 helper / handler 说明
/v1/chat/completions 或 /pg/chat/completions RelayModeChatCompletions TextHelper 普通文本/多模态聊天主链路。
/v1/completions、/v1/edits、/v1/moderations Completions / Edits / Moderations 默认 TextHelper 没有专门 case 时落到文本 helper。
/v1/embeddings 或 path 以 embeddings 结尾 RelayModeEmbeddings EmbeddingHelper /v1/engines/:model/embeddings 也靠后缀命中。
/v1/images/generations、/v1/images/edits RelayModeImagesGenerations / RelayModeImagesEdits ImageHelper 图片生成/编辑的请求校验、上游转换和响应解析在 image helper + adaptor 中完成。
/v1/audio/speech、/v1/audio/transcriptions、/v1/audio/translations RelayModeAudioSpeech / AudioTranscription / AudioTranslation AudioHelper Distributor 还会给 speech/transcription/translation 补默认模型。
/v1/responses/compact、/v1/responses RelayModeResponsesCompact / RelayModeResponses ResponsesHelper compact 要先判断，因为它也是 /v1/responses 前缀。
/v1/rerank、/v1/realtime RelayModeRerank / RelayModeRealtime RerankHelper / Realtime WebSocket 链路 Realtime 入口先升级 WebSocket，再进入对应 relay 格式处理。
/v1beta/models/*、/v1/models/* RelayModeGemini geminiRelayHandler 模型名通常从 path 中提取，而不是只从 body.model 读取。
/mj/* Path2RelayModeMidjourney(path) RelayMidjourney / Midjourney task handler Midjourney 是单独的 path 子分类，不走普通 chat/image/audio helper。
Path2RelayMode 返回 Unknown，但中间件已设置 relay_mode 例如 RelayModeVideoSubmit / RelayModeVideoFetchByID RelayTask / RelayTaskFetch 视频、Suno、Kling、Jimeng 等任务入口主要靠 Distributor 或转换中间件补充 relay_mode / platform。

Group 如何串联 User、API Key、Channel

User 的 group 是默认归属，API Key 的 group 是本 key 请求时希望使用的目标分组，Channel 的 group 是这个渠道能服务哪些分组。

界面里的“用户可选”勾选就是这层白名单。 分组管理中勾上“用户可选”会进入 UserUsableGroups；特殊可用分组规则 GroupSpecialUsableGroup 会按用户默认组做额外增删。它们不会改变用户所属组，只决定用户可以创建或选择哪些 token group。

Channel 选择关系图

把 candidate_channels = channels where group contains effective_group and models contains request.model 拆成两个肉眼可见的筛选条件：先看 group 是否服务本次请求，再看 model 是否支持本次模型。

更口语化地说：一次请求会拿着两张“门票”去找渠道：一张是 effective_group，一张是 request.model。某个 channel 只有在“服务分组列表里有这张 group 票”并且“模型列表里有这张 model 票”时，才会进入候选池。进入候选池以后，才轮到优先级、权重、重试等规则。

G单次请求的 effective group

单次请求最终只会使用一个有效分组。token.group 非空且在该用户可用分组集合里时，优先使用 token.group；否则回退到 user.group。

effective_group = token.group || user.group 然后 candidate_channels = group + model 命中

K归属与可用集合不是一回事

User.group 是“用户所属默认组”，是单值；UserUsableGroups 是“这个用户允许选择哪些目标 group”的白名单集合。集合不是用户同时属于多个组，而是 token/playground 可以切换到哪些被授权的目标组。

快速记忆

看代码时可以按下面的口径定位问题。

Endpoint 决定入口形态

/v1/chat/completions、/v1/images/generations、/v1/video/generations 先把请求分到不同的 controller/helper/task 链路。

RelayMode 决定 helper

普通同步 relay 用 Path2RelayMode 推断，然后在 relayHandler 中选择 Text/Image/Audio/Responses 等 helper。

Group + Model 决定候选渠道

effective group 与 request.model 命中 ability 后，才会在候选渠道里按 priority/weight 选择具体 channel。

channels.type 决定上游协议

选中 channel 之后，type 才开始发挥作用：同步调用找普通 adaptor，异步任务找 task adaptor。
